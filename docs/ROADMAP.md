Updated: 2026-09-30  
Current baseline: `V4.0.0-dev61`  
Production gateway baseline: `gateway-v61`

**已经确认的产品要求仍以 `PRODUCT_REQUIREMENTS.md` 为准。** 本路线图负责安排顺序，不把候选想法自动变成需求。

## 产品目标

SCFA 内容中心面向《最高指挥官：钢铁联盟》Steam 版玩家，目标是把地图和 MOD 的发现、安装、更新、冲突处理、备份恢复与管理员发布集中到一个安全的 Windows 客户端中。

长期原则：

- 玩家操作优先保证本地文件安全，不猜测、不静默覆盖冲突内容。
- 普通玩家客户端不持有长期 COS 写入密钥。
- 地图/MOD 只有管理员可以正式发布。
- 发布版本与游戏内部版本分开管理并分别校验。
- 自动同步不自动降级本地较新版本。
- 不恢复已取消的玩家投稿/审核工作流。
- 生产服务器事实以 `PROJECT_HANDOFF.md` 为准；Codex 不凭聊天记忆猜生产状态。

## Codex 当前执行顺序

如果产品负责人没有给出新的更高优先级任务，Codex 从这里开始：

### P0-A：客户端更新下载后的 SHA-256 文件句柄问题（源码已修复，2026-09-30）

当前 `UpdateService.DownloadAsync` 在输出 `FileStream` 仍以 `FileShare.None` 打开时，就重新打开同一文件计算 SHA-256。

目标：

- 明确 flush/dispose 下载输出流后再计算哈希；
- 保留大小校验、下载进度、取消和失败清理；
- 添加能复现并防止回归的测试；
- 不降低现有 PE、路径和 SHA-256 安全校验。`UpdateService.DownloadAsync` 已在 Windows 上完成“修复前失败、修复后通过”的回归验证；真实发布包的更新验收仍待执行。

### P0-B：Publication Gateway 的 COS 超时策略（源码已修复，2026-09-30）

`CosTransport` 的共享 `HttpClient` 仍不设置全局期限；各 COS 操作现在使用覆盖响应头、错误正文和数据流的独立关联期限：元数据 45 秒、小对象 5 分钟、大包 12 小时。超时安全映射为 HTTP 504，调用方取消仍保持取消语义。隔离回归已通过；真实 COS 场景仍待生产验收。

目标：

- 为 COS 请求建立明确、可测试的超时/取消策略；
- 元数据/小对象请求不能无限等待；
- 大包上传/下载不能因为过短的全局超时被误杀；
- 为超时、取消和错误映射增加回归覆盖。

### P0-C：PublicationCoordinator 锁范围

当前 commit / unpublish / restore 共享 manifest 串行锁，这是为了防止丢更新，**不能直接删除**。

目标：

- 保留最终 manifest 变更的串行化；
- 评估把耗时的 COS 下载/包校验移出最终写入临界区；
- 在真正写 manifest 前重新读取并做冲突/哈希检查；
- 增加并发/冲突回归测试。

### P1：网关健康接口提供安全版本信息

目标：

- `/publication-healthz` 增加安全的版本/构建标识；
- 不返回密钥、路径或私有配置；
- 部署验收可以直接确认“当前跑的是哪个版本/构建”。

### P0-D：把 updater v2 纳入源码管理

2026-09-30 已在生产服务器旁路验证 updater v2 原型，但它目前不属于仓库正式源码，systemd 也没有切换到它。

Codex 应把已验证行为整理成可审查的仓库部署工具，包括：

- report-only；
- 完整 Release 大小校验；
- 实时总进度/分块进度；
- 分块缓存复用；
- Release SHA-256 校验；
- staging；
- 当前二进制备份；
- 原子切换；
- health/auth 验证；
- 运行中二进制 SHA-256 验证；
- 失败后回滚并再次验证健康和旧 SHA-256；
- 清晰的 `UPDATE_OK` / `UPDATE_FAILED` / `ROLLBACK_OK` / `ROLLBACK_FAILED` 结果。

**Codex 只负责源码和部署材料；不要直接启用生产 timer。**

## P0：V4.0 正式发布前仍需完成

### 1. MOD 完整发布闭环

- 软件内发布真实 MOD。
- 玩家客户端安装。
- 再次同步确认不会重复下载。
- 发布新版本并验证安全更新、备份和版本判断。
- 必要时验证失败恢复。

### 2. 下架 → 档案 → 恢复闭环

代码与生产 `gateway-v61` 已就绪，但真实管理员验收仍未完成：

- 管理员下架地图/MOD；
- 玩家端不再看到正式条目；
- 管理员档案页能找到历史/下架版本；
- 恢复指定版本；
- 验证公开 manifest 和玩家端刷新/安装/同步行为。

### 3. 正式客户端更新链验收

先完成 P0-A 文件句柄修复。

然后：

- 使用真实发布包验证更新检查、下载、SHA-256、应用与清理；
- 验证启动失败时旧版本恢复；
- 验证重复检查不会损坏已下载/已安装状态。

### 4. Steam 兼容性发布检查

- 保留自动结构/路径/版本/哈希检查；
- 建立管理员可执行的 Steam-vs-FAF 人工检查清单；
- 未确认兼容的内容不得标记为已自动验证。

## 明确不做

- 不恢复普通玩家投稿与管理员投稿审核。
- 不把长期 COS SecretId/SecretKey 写进玩家客户端。
- 不为了自动同步而覆盖无法确定身份的重复目录。
- 不把 FAF 专属行为未经验证地当成 Steam 版兼容。
- 不根据旧 V3/Win32 文档重新设计当前 WPF 客户端。
- 不因为服务器下载慢或 403/502 就重装系统或盲目改业务代码。

## 如何更新本路线图

- 产品负责人确认的新要求：先写入 `PRODUCT_REQUIREMENTS.md`，再安排到本文件。
- 完成一个阶段：更新当前阶段，不追加几十段版本流水账。
- 具体生产事实：写入 `PROJECT_HANDOFF.md`。
- 测试/发布门槛：写入 `BUILD_VALIDATION.md`。
- 重要开发/部署/排障：追加到 `OPERATION_LOG.md`。
